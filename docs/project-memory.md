## 0. 先读这里：这份文档怎么用

这不是实现手册，也不是要求每次任务机械执行的固定流程。它的作用是让新 Agent 先理解项目是什么、哪些决策长期有效、当前状态在哪里、用户希望怎样协作，再根据实际任务的风险和范围选择合适的调查、修改、测试和记录方式。

项目状态会变化。发现本文档与当前代码、配置、日志或专项文档不一致时，应以当前事实为准，并在完成核对后更新本文档的相关状态，而不是照搬旧结论。

### 事实优先级

一般按以下顺序判断当前事实：

1. 当前工作区代码、配置、运行日志和实际验证证据；
2. 最新的专项维护文档；
3. 本文档的“当前快照”；
4. 最新会话浓缩；
5. 更早的会话、临时任务和历史建议。

旧记录仍然有价值，尤其是“为什么这样设计”和“哪些方案已经被否决”，但历史方案不能自动视为当前实现。

### 生产与证据边界

Agent 可以在本工作区分析、编辑、构建、运行测试副本并准备交付材料；**不能代替用户或运维访问、停启、替换、回滚或确认生产服务器**。生产服不存在于本机，Agent 也无法推送/部署到生产；生产部署、推送与生产实测只能由用户/运维执行并提供证据。

以下状态互不等同，应分别记录：

- 代码或脚本已修改；
- 本地构建、冷启动或测试副本已验证；
- 生产候选文件已准备；
- 生产已部署或已实测；
- 远程仓库已提交或已推送。

建议使用的状态词：当前基线、已本地验证、测试副本验证、生产待确认、生产已观察（附证据）、实验性、待用户/运维执行、已替代、已废弃、未验证。

### 启动与脚本加载日志优先级

2026-07-30 已直接运行 `mdtserver/start-server.ps1` 复核日志链路可用。后续进行冷启动、编译或脚本加载诊断时，优先使用项目自带的正式日志，不再默认在项目根目录生成重定向临时日志：

- `mdtserver/config/logs/log-0.txt`：当前 Mindustry/MindustryX 运行日志，可确认 ScriptAgent 汇总、`Server loaded`、端口开放和地图加载；
- `mdtserver/config/logs/script-load/current.log`：当前脚本逐项加载、编译、数据库初始化和业务模块启动日志；
- `mdtserver/config/logs/last.log`、`mdtserver/config/logs/script-load/last.log`、`last-error.log` 及各自 `history/`：由启动脚本在上一轮归档或进程正常退出后维护，适合复查已结束/上一轮启动。

只有上述正式日志缺失、没有随本轮启动更新、损坏，或确实无法覆盖启动器自身输出时，才创建一次性根目录临时日志；诊断结论写入文档后应及时清理。清理临时产物时不得删除 `config/logs` 正式日志，也不得触碰数据库、外部 CP、缓存备份或其他运行数据。

### 本地服务器启动与命令 Socket 调试要点（2026-08-03 实测）

- 正常启动用 `mdtserver/start-server.ps1`（自带 `-Dfile.encoding=UTF-8`、Java logging 配置与异常退出重启）。`start-server.ps1` 会把 `server.properties` 的 socket 相关项拼成多条 `config socketInput*`（如 `config socketInputPort 6859`、`config socketInputAddress localhost`、`config socketInput true`）追加到启动参数。
- **命令 Socket 竞态**：ServerControl 的 `Trigger.socketConfigChanged` 对每条 `config socketInput*` 执行 `toggleSocket(false)+toggleSocket(true)`；多条连续触发会让 accept 线程在重启竞态中死亡，`log-0.txt` 出现 `[E] Command input socket already in use...` 与 `java.net.SocketException: Socket is not bound yet`，TCP 能连上 6859 但命令无回显。
- **规避**：直接以 java 命令行启动、只传单条 `config socketInput true`（不带 port/address，用默认 6859/localhost），socket server 只启动一次，命令回显正常。
- **命令通道**：`hookGameHandler` 把 `ServerControl.handler` 反射替换为 `MyCommandHandler("", Config.serverCommands)`，命令 Socket 与游戏内 `/sa`、`/cp`、`/externalcp` 共用框架命令根；原生命令仍由原生 handler 执行。已验证 Socket 上 `cp files`、`cp load 11`、`externalcp list` 正常回显（UTF-8）。
- **自动化启动**：`java <JVM参数> -jar server-2026.07.20.B480-mdtdo.jar "config name ...,config port 6567,...,config socketInput true,playerlimit 16,shuffle all,host"`，stdin 走管道即可（JLine 退化为 dumb terminal），命令回显在 stdout 与日志文件。
- **退出与清理**：socket `exit` 在脚本停用后可能不生效；stdin EOF 触发 JLine 退出路径并遇到项目既有的 ScriptAgent 集中卸载停滞，进程可能不退出。清理时结束 java 进程树并确认 6567/6859/10099 端口释放；临时改过的 `server.properties` 要从备份还原。

## 2. 项目定位与整体地图

MDT DO 是一个完整的 Mindustry 专服产品，而不是若干互不相关的脚本。玩法、账号与数据库、网络同步、资产、权限、运维、运行环境和文档互相影响；遇到单个脚本看不懂时，应扩大到调用链、模块依赖、服务端版本和玩家体验，而不是孤立地修补一处。

主要区域：

- mdtserver/config/scripts：插件总目录；
- mdtserver/config/scripts/mapScript：地图与地图标签玩法；
- mdtserver/config/scripts/coreMindustry：菜单、积分板、基础框架；
- mdtserver/config/scripts/wayzer：主要业务、账号、信任、技能、商店、投票、数据库、权限与保护逻辑；
- docs：维护总览、领域设计、兼容说明、验证记录；
- 参考项目：官方 Mindustry、MindustryX 和 ScriptAgent 的源码/版本参考；
- session浓缩：历史会话输入，不是当前实现的最高事实源。

参考项目/MindustryX-main 是独立的补丁式参考仓库，目录内有自己的 AGENTS.md；只有在修改该嵌套仓库时再读取并遵循，不能把它误当作 MDT 根项目的固定流程。

运行中的数据库、日志、缓存、外部 CP、音乐、资产和备份属于运行数据或交付材料，和可提交的源码/文档分开管理。

## 3. 用户偏好与协作边界

以下是从用户长期要求中提炼的默认画像，不替代用户在当前任务中的新指示：

- 用户维护的是长期运行的专服产品，首要关心稳定性、状态正确性、玩家能正常进服/重生和既有玩法不被破坏。
- 用户偏好先理解现状、影响面和风险，再高执行力地完成已经对齐的小任务；不喜欢凭猜测边改边试，也不希望为小问题堆叠新系统。
- 架构、版本、协议、数据库、权限、生产和不可逆行为等大范围改动，通常先调查源码/文档、说明取舍和回滚方式，等用户确认后实施。
- 改动完成后希望看到真实的验证证据、未覆盖边界、风险和下一步，而不是笼统的“已完成”。
- 本地修改、测试、提交、远程推送和生产部署是不同动作。用户明确要求提交时再提交；远程推送和生产替换仍应单独确认。生产部署不能由 Agent 完成。
- 用户偏好少引入系统、复用现有结构、保留可回滚路径；对生产锁死、数据损坏、玩家无法进服、旧状态回放和不可逆权限扩大容忍度低。
- 真实数据、封禁记录、数据库、备份和运行文件不应被擅自破坏、清理或混入提交。
- 汇报以中文、结构化、简洁、可追溯为宜；信息不足的会话如实记录，不为凑篇幅臆测扩写。

“直接做”和“重大改动先确认”并不矛盾：按风险、影响范围和授权范围判断。用户对当前任务的新要求优先于这里的默认偏好。

## 4. 长期设计不变量

这些是帮助 Agent 做取舍的长期边界，不是把每个任务锁成同一套操作步骤。

### 4.1 稳定性与正确性优先

正确的玩家状态、原生生命周期、可靠性和可恢复性优先于表面上的限流效果、单项指标或新功能数量。不能为了“看起来生效”破坏底层顺序、可靠包语义或已有回滚链路。

### 4.2 网络压力与游戏性能分层

总网络流量、世界/资产/音乐/CP 传输、游戏同步、TPS 和实体规模是不同概念。资源传输尖峰可以影响排队、并发和观察，但不应误触发清单位、暂停玩法、换图或永久阻塞入服；破坏性性能措施只能由与其直接相关的游戏状态证据驱动。

### 4.3 失败时可恢复，优先放行

门控、队列、监控、热加载、反射兼容、异步任务和协调器应有界、可取消、有超时，并在异常、离线、换图、重置和卸载时释放状态。无法取得可靠状态时，宁可回退原生流程或放行，也不能永久锁住新玩家、主循环或后续任务。

### 4.4 一个职责尽量只有一个权威执行者

实验入口、兼容入口和旧入口不应与正式系统并行改变同一类状态。新增机制前先确认现有执行器、缓存和回滚链路，避免两套清理、同步、暂停或权限判断互相覆盖。

### 4.5 兼容层隔离版本差异

版本专属 API 尽量集中在兼容层并安全降级；可选端、数据库驱动和脚本类加载器之间只暴露稳定的数据契约。升级游戏、MindustryX 或 ScriptAgent 时，应先确认上游实际变化，不因版本号变化就自动复制旧方案。

### 4.6 权限最小化与数据边界

权限按层级和真实主体在执行时复核，敏感操作尽量可审计、可撤回；运行数据、数据库、日志、缓存、外部内容和备份不默认进入源码提交，也不因清理缓存而误删业务数据或回滚材料。

### 4.7 历史方案不能自动复活

曾经存在的代码、旧端接口或聊天提案不代表当前版本仍适用。恢复历史功能前要重新确认版本兼容、生命周期、卸载行为、玩家状态和真实风险；被明确否决的方向应保留原因，防止后续 Agent 误恢复。

## 7. 已替代或明确不应恢复的方向

以下不是实现清单，而是给续接 Agent 的防误用提示：

- 不恢复旧版本逐玩家手工实体序列化、取消原生包后统一重发或隐藏实体接管；
- 不把关键可靠状态降级为不可靠传输，也不以跨 TCP/UDP 的旧实体状态重放来“修复”同步；
- 不把世界、资产、音乐或 CP 传输当作游戏实体压力，不让它们直接触发清单位、暂停玩法、换图或永久入服等待；
- 不重新引入会因确认丢失而锁住全服新连接的插件入服预留/门控；
- 不维护第二套并行的性能清理/暂停/换图执行器；
- 不把运行中的完整世界/资产握手宣传为无副作用的单资产热同步；
- 不恢复旧的 ScriptAgent 本地字节码 workaround；当前上游维护构建仍是未发行候选，不能自动视为正式版本、稳定生产基线或已部署状态。
- 不恢复旧 `[危险]服务器测试模式`、`test:<account:id>` 临时主体、临时MDC/资历覆盖或固定结算×10；测试需求应通过已拆分的最小服务器功能开关处理。

如果未来上游提供了新的可靠能力，应重新阅读源码、验证时序和回滚行为后再决定，不因“过去曾经这样做过”直接恢复。
