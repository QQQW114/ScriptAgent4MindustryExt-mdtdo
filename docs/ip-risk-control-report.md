## 0. 结论摘要

1. **规则数量**：`IPG` 共 11 类规则/机制（R1–R11）+ 1 类"只记录不处罚"的观察机制（R12）；其中真正会改变玩家状态的只有 5 类动作：标记风险 IP、风险游客强制观战、风险游客聊天/投票/踢出禁言、风险 IP 禁止注册、同 IP 换身份广播。
2. **核心触发是"封禁关联"而不是行为阈值**：可见脚本日志窗口（2026-10-01 ~ 10-10）内共有 **60 条去重后的风险 IP 标记**，覆盖 **8 个 IP**，**100% 的原因都是 `禁封账号尝试进入: ...`**；由"投票踢出 2 次/24h"阈值触发的标记在窗口内为 0 条，管理员手动标记也为 0 条。可见的近期触发：10-07 单日 32 条为峰值，窗口内最后一次为 **2026-10-09 22:52:51**。
3. **续期放大器**：每次被封账号重连都会重新执行 `markRiskIp`，把该 IP 的到期时间刷新为 `当前时间 + 24h`（`IPG:463-478` + `ban.kts:223-231`）。日志证据：`123.246.110.231` 在 2026-10-07 22:44:10–23:41:57 之间被标记 **22 次**（约 1 小时内），`183.192.135.240` 在 10-06~10-09 被标记 **17 次**。持续重连可让一个 IP 的实际风险期远超 24h。
4. **阈值设计被重连路径旁路**：投票踢出本应"同 IP 24h 内 2 次才标记"，但 10-04 23:28:25 的一次投票踢出之后 **5 秒**（23:28:30）同一 IP 就因被封账号重连被标记，4 分钟内标记 6 次，并把另一个 IP 也标记了（疑似同一被封玩家换网络，推断）。窗口内 9 条踢出计数全部停在 `1/2`，从未由阈值路径触发。
5. **误伤面主要落在共享出口**：风险 IP 的唯一豁免条件是"当前会话已登录（`PlayerData.authed`）"，因此 NAT/宿舍/校园网/运营商 CGNAT 出口下的**未登录新玩家**会替同 IP 的捣乱者"连坐"：强制观战 + 聊天/投票禁言 + 禁止注册，最长可持续到"最后一次重连 + 24h"。日志里 8 个风险 IP 中，`183.192.135.240` 与 `183.192.135.17` 属同一 /24，符合动态 IP/家庭多设备特征。
6. **绕过面**：换游戏 UUID 可避开封禁检测与"被封账号重连"标记；连接后再 `/login` 登录**已被封禁的账号**不会重新校验封禁（`accountAuth.kts` 登录流程无封禁检查），且登录成功会解除风险 IP 的强制观战（`IPG:563-571`）——存在"新 UUID 进服 → /login 被封账号 → 正常游玩"的完整绕过链。VPN/换网/第二个账号同样可绕过。Steam 特例地址（`steam:*`）会被当成"本地/内网"整体忽略（`module.kts:46-49` + `IPG:82`），实际影响**未确认**。
7. **同 IP 小号广播量很大**：旧原生日志 2026-09-26 ~ 10-16 共记录 **293 条**"可能为小号"全服广播（日均约 17 条，峰值 46 条/日；10-14/15/16 仍有 7/11/7 条）。同一对身份在 60 秒去重窗口外可反复广播（日志中同一 IP 的 A↔B 身份对重复 11+11 次）。广播会公开上一身份的名字、**完整游戏 UUID** 与短 ID，公共出口误报时会形成公开误指。
8. **与"高人数同 IP 多账号清理"不冲突但策略相反**：`forceObAutoCleaner.kts` 的同 IP 清理只在在线 ≥14 人时踢"同 IP 多余已登录账号"（保护 3++/4），与 `IPG` 的"允许同 IP 多账号"不共享数据、互不触发；但风险 IP 游客不会被该清理逻辑处理，可能长期占用观战位（见 Q5）。
9. **持久化可靠但有 fail-open 风险**：风险记录/索引/上次身份/踢出计数全部落在 H2 库的 `MdtSettings`（跨重启生效）。但 `riskRecord` 把索引键当作"快速否定"判据（`IPG:379`）：若索引缺失/与单 IP 记录不一致，即使单 IP 记录仍在，风险限制也会**静默失效**；且"写单 IP 记录"和"写索引"是两个非原子事务。
10. **可观测性不足**：脚本只有 4 处 logger（标记、踢出计数、拒绝注册、身份切换），**没有**记录风险解除、过期释放、强制观战/禁言实际发生、管理员操作等事件；因此"风控实际拦截了多少人"无法从日志回答。窗口内也没有任何"拒绝注册"日志，说明该窗口内没有发生被拦截的注册尝试。

补充：

- 纯 IPv6 地址不会被 `ipv4Regex` 命中，`isLocalOrPrivateIp` 对"不是 4 段点分"的地址只把 `steam:` 当本地，因此其他 IPv6 会以完整字符串作为风险键（没有被忽略，也没有做 /64 聚合）。
- `IPG:402` 没有像其他脚本那样回退 `player.ip()`（对比：`securityGuard.kts:531`、`forceObAutoCleaner.kts:61-62`、`accountAuth.kts:106-107` 都写成 `player.con?.address ?: player.ip()`）。连接对象为空时 `IPG` 会得到 `unknown` 并**放行**（fail-open）；在线玩家 `con` 通常非空，**实际是否触发未确认**。
- 全库 grep `con?.address|con.address|.ip()` 共 75 处，其中真正参与风控动作的只有 `accountIpGuard`、`securityGuard`、`forceObAutoCleaner`、`ban` 调用链；`ipRegion`、`welcomeMsg`、`regionAutoLang`、`coreMindustry/variables.kts:59` 均属展示；`playerRecognition`/`playerReputation` 用 IP 做"同 IP 互相赞踩/认可"限制，不涉及入服风控。

## 3. 规则清单（阈值 / 窗口 / 动作 / 代码位置）

### R1 管理禁封 → 立即标记风险 IP

- 触发：`ban.kts` 的 `ban()` 中，只要原因**不以 `投票踢出` 开头**（管理 `/banX`、面板封禁等）。
- 动作：`markRiskIpForPlayerData(data, "账号被禁封: <原因>", operator)`；在线优先用当前连接 IP，离线回退 `last_ip`。
- 时长：`riskIpDurationMillis` 默认 24h（`IPG:20`）。
- 位置：`ban.kts:241-248`、`IPG:483-496, 463-478`。

### R2 被封账号尝试重连 → 标记风险 IP

- 触发：`PlayerConnect` 时 `store.findNotEnd(PlayerData[player].id)` 命中未到期玩家封禁（`banStore.kts:106-109`）。
- 动作：先 `markRiskIpForPlayer(player, "禁封账号尝试进入: <封禁原因>")` 再踢出。
- 特点：**每一次重连尝试都会重新标记并刷新 24h**（`RiskIpRecord.until = now + 24h`），不判断该 IP 是否已在风险中。
- 位置：`ban.kts:223-231`、`IPG:463-478`。

### R3 投票踢出计次 → 达阈值标记风险 IP

- 触发：`ban()` 中原因以 `投票踢出` 开头（投票踢出统一走 60 分钟封禁，`voteKick.kts:52-68`）。
- 计数：`recordKickForIp` 按 IP 记录 `at/subjectKey/displayId/reason`，窗口 `kickRecordWindowMillis` 默认 24h，并清理窗口外记录。
- 阈值：`kickRiskThreshold` 默认 2；达到/超过时 `markRiskIp("同IP 24小时内账号被踢出 N 次：<原因>")`；之后再被踢仍会继续标记并续期。
- 位置：`ban.kts:241-248`、`IPG:498-545`、`IPG:25-26`。

### R4 风险 IP 的未登录玩家强制观战

- 判据：`!PlayerData[player].authed && riskRecord(playerIp(player)) != null`（`IPG:404-405`）。
- 动作：`teams.changeTeam(player, teams.spectateTeam)`，记录到 `riskGuestUuidsByIp`；进入时拦截 `AssignTeamEvent` 再兜底一次。
- 位置：`IPG:420-425, 606-611, 613-619`；`BetterTeam` 观察者队伍。

### R5 风险 IP 的未登录玩家"轻量禁言"

- 动作：拦截 `OnChat` 包（`received=true`），阻断：普通聊天 + `t/a/vote/投票/votekick/kick/踢出` 这些命令；其他命令（含 `/login`、`/help`、菜单类）**不拦**。
- 提示：每 `riskTipIntervalMillis` 默认 30 秒最多一次（`IPG:21,407-418`），提示剩余时间与原因，并引导 `/login`。
- 位置：`IPG:585-593, 631-636`。

### R6 风险 IP 禁止注册新账号

- 触发：注册流程 `accountAuth.registerFlow` 开头调用。
- 动作：回复拒绝消息 + `logger.warning("[账号IP防熊] 拒绝 ... 在风险IP ... 注册新账号")`，返回 false 中止注册。
- 位置：`accountAuth.kts:525-550`（调用点 535）、`IPG:573-583`。

### R7 风险 IP 不拦截登录，登录后解除未登录限制

- `allowAccountLogin` 只记录最近身份（10 分钟内存观察），**恒返回 true**（`IPG:557-561`）。
- 登录成功后 `onAccountAuthed`：若当前在观察者队伍且属于风险游客 → 切回普通队伍并提示；随后 500ms 后做一次同 IP 换身份检查。
- 位置：`IPG:557-571`、`accountAuth.kts:406,426`。

### R8 同 IP 换账号/UUID → 全服"可能为小号"广播（只提示，不处罚）

- 数据：`account.ipLast.<ip>` 保存该 IP 上一次身份的 `subjectKey/displayId/name/uuid/at`。
- 条件：距上次 ≤ `altBroadcastWindowMillis`（默认 24h）、主体不同、**游戏 UUID 不同**（同一游戏 UUID 的正常登录态切换不报）、`altBroadcastEnabled=true`。
- 动作：全服广播 + `logger.info("[账号IP防熊] 同IP身份切换: ...")`；`claimAltBroadcast` 对 `(ip, 前主体, 当前主体, 当前uuid)` 做 60 秒去重。
- 执行时机：`PlayerJoin` 后延迟 `altBroadcastDelayMillis`（默认 3s）；登录成功后延迟 ≤500ms。
- 位置：`IPG:274-373`。

### R9 管理指令面板 `/ipguard`

- 权限 `wayzer.admin.ipguard`，`registerDefault(..., group = "@admin")`；指令体内再做一次 `hasPermission` 校验。
- 子命令：`status`（显示开关/阈值/风险数/临时观战数，**硬编码显示"单IP多账号: 允许"**）、`check <ip>`（旧绑定、上一身份、最近身份数/USID 数、踢出记录、风险状态、本脚本观战记录）、`risk <ip> [原因]`、`unrisk|unblock <ip>`、`release <ip>`（风险仍生效时拒绝）、`unbind <ip>`（删旧版绑定）。
- 位置：`IPG:660-749, 751`。

### R10 过期/清理机制

- 风险记录：惰性判定，访问时发现 `until <= now` 才删除并异步释放观战残留（`IPG:386-392`）；`status` 时会顺带从索引剔除过期 IP（仅 `guardEnabled=true` 时回写，`IPG:446-461`）。
- 踢出计数：读取时删除窗口外记录并回写（`IPG:239-251`）。
- 上次身份 `ipLast`：**无过期、无清理**，仅被覆盖（`IPG:188-198`）。
- 内存态在 `ResetEvent` 清空（`IPG:647-658`），数据库不变。

### R11 忽略规则与总开关

- `guardEnabled=false` 时 `shouldIgnoreIp` 恒 true → 标记/计次/风险判定全部失效（`status` 仍能读库展示）。
- `ignoreLocalIp=true`（默认）时忽略内网/本地/`steam:*`/`unknown`。
- 被忽略 IP 上管理员 `/ipguard risk` 会返回"未标记"。
- 位置：`IPG:17-18, 79-93, 463-465`。

### R12（观察类，不处罚）短时同 IP 多身份统计

- 10 分钟窗口内记录同一 IP 出现的 `subjectKey/usid/uuid`，仅 `/ipguard check` 展示"最近身份数 / 最近 USID 数"，不拒绝入服、不触发任何动作。设计上明确"仅统计不拒绝入服"（`IPG:19`）。
- 位置：`IPG:19, 253-260, 595-604, 700-701`。

### 4.2 跨重启与加载时序

- 风险记录写库 → **跨重启保留**；`onEnable` 异步加载索引缓存（`IPG:621-629`）。
- 索引未加载完成前，`riskRecord` 会退化为逐个 IP 查库（`IPG:379` 条件不成立），行为仍正确。
- `lastIdentityByIp`、`kickRecordsByIp` 首次使用时懒加载并缓存；`recentByIp`、`riskGuestUuidsByIp`、`lastRiskTips`、`scheduledAltChecks`、`recentAltBroadcasts` 均为**纯内存**，重启丢失（丢失后：风险判定仍按库中 `until` 生效，玩家进服时重新强制观战，因为 `PlayerJoin/AssignTeam` 会再检查）。

### 4.3 清理与一致性

- 过期风险记录只在"再次被查询到"时删除（没人查就一直留到下一次），`status` 只回写索引、不删单 IP 行；因此库里可能残留 `until < now` 的行（不生效但占位）。
- `setSetting(key, null)` **不会删除行**，只会把 value 置 NULL（`MdtStorage.kt:1060-1083`），所以"解除/过期"后 `account.ipRisk.<ip>`、`account.ipKick.<ip>` 行会以 NULL 值长期保留。
- **非原子写**：`markRiskIp` 先写单 IP 记录、再写索引，两个独立事务（`IPG:472-474`）；`clearRiskIp` 亦然（`IPG:550-551`）。
- **fail-open**：`riskRecord` 在索引已加载时用 `if (ip !in riskIndexCache) return null` 做快速否定（`IPG:379`）。即**索引是风险限制的强制判据**；若单 IP 记录存在但索引缺失/损坏（例如只恢复了一半数据、旧版本写入、索引被误清），该 IP 的风险限制会静默失效，`/ipguard check` 也查不到（同样走 `riskRecord`）。反之索引有、记录无则安全（查不到记录 → 放行）。
- 数据保留：`ipLast` 每个出现过的 IP 永久保留一行（含完整游戏 UUID、账号主体 ID、玩家名）；`ipKick`/`ipRisk` 行解除后保留 NULL 行。**无保留期/清理任务**。

## 5. 与权限层级的关系

### 5.1 `IPG` 本身不读信任等级

- `IPG` 只认一个身份状态：`PlayerData.authed`（`PlayerData.kt:10-19`：`id != uuid` 即视为已登录/已绑定）。
- 代码中没有任何 `trustLevel` / `hasTrustLevel` / `player.admin` 判断（grep `IPG` 无相关命中）。因此：
  - 游客（信任 0）→ 受风险 IP 全部限制；
  - 任何**已登录**账号（0/1/2/3/3++/4 级）→ 不受风险 IP 限制；
  - **未登录**的 3++/4 级玩家若从风险 IP 进服，同样会被强制观战 + 禁言（因为未登录会话在权限系统里也被当作 0 级游客：`trustLevel.kts:286-296` 会剥离未登录会话的 `@admin` 与历史主体权限）。
- 实际影响有限：管理/常驻玩家通常会被 UUID+USID 自动登录（`accountAuth.kts:724-739`）→ 进服前即 `authed` → 不受风险 IP 影响；只有"清空客户端数据/换设备导致自动登录失败"时才会以游客身份撞上风险 IP 限制。

### 5.2 管理面权限

- `/ipguard` 需要 `wayzer.admin.ipguard`：`registerDefault(..., "@admin")`（`IPG:751`），4 级/原生 admin 默认拥有；**3++ 协管白名单中没有该权限**（`trustLevel.kts:267-284`）；指令体内二次校验（`IPG:664-666`）。
- 3++ 可以在 `/security` 菜单里**只读**查看风险 IP 列表（`securityGuard.kts:986-995`，依赖白名单中的 `wayzer.admin.security`，`trustLevel.kts:276`），不能标记/解除。
- 对比相邻系统的层级保护：
  - 高人数同 IP 多账号清理：默认保护 3++/4/admin（`forceObAutoCleaner.kts:25-26, 90-93, 111`）；
  - 安全风控：原生 admin 不受聊天/菜单限速（`securityGuard.kts:535, 1098-1099`），IP 封禁解除需 `isTrustAdmin || isPluginAdmin`（`securityGuard.kts:444-447`）。
- 结论：**"IP 风控"目前没有针对 3++/4 的任何显式豁免**；豁免只来自"是否已登录"。

## 7. 风险与问题

> 严重度：🔴 高 / 🟠 中 / 🟡 低。

### Q1 🔴 共享出口连坐（主要误伤面）

- 风险键只有"精确 IP 字符串"，没有 NAT/共享出口识别、没有 /24 聚合、没有白名单。
- 受影响的是"同 IP 的未登录玩家"：被强制观战 + 聊天/投票禁言 + 禁止注册；而注册本身还要求"本次启动累计在线满 1 小时 + 验证码"（`serverFeatureSettings.kts:77,88,116` 默认开启；`accountAuth.kts:66-67` 判定、`536` 注册前校验验证码），所以新玩家在该 IP 上的实际可玩路径基本被切断。
- 证据：60 次标记命中 8 个 IP，其中至少 `183.192.135.x` 的 .240/.17 属同 /24；`123.246.110.231` 单 IP 22 次重连说明"一个人捣乱，整条出口/整户家庭被连坐"。
- `ban.kts:223-231` 标记的是**当前重连者 IP**，`IPG:483-496` 离线封禁回退 `last_ip`（可能已被运营商回收给别的用户/家庭）。

### Q2 🔴 重连续期 → 实际限制期无上限

- `markRiskIp` 每次都覆盖 `until` 为 `now + 24h`（`IPG:463-478`），R2 在每次重连都触发（`ban.kts:223-231`）。
- 只要被封者每隔 <24h 重连一次（脚本连"是否同一身份重复尝试"都不判断），该 IP 的风险状态就永久存在。日志中 22 次/1 小时、17 次/4 天的两组就是实例。
- 建议视为"放大器"缺陷，而不是 24h 限时。

### Q3 🟠 封禁/风控绕过链

1. **换游戏 UUID**：封禁检测是 `store.findNotEnd(PlayerData[player].id)`（`ban.kts:225`），当前 ID 是游客 UUID 或账号主体；换 UUID + 换 USID 后自动登录失败（`accountAuth.kts:724-739` 只认 uuid+usid）→ 以新游客身份进服，不命中封禁，也不会触发 R2 标记（前提是该 IP 尚未因别的原因被风险标记）。
2. **连接后 `/login` 被封账号**：`finishLogin`（`accountAuth.kts:399-456`）只检查账号状态/客户端绑定/重复在线（`380-397`），**不查 `PlayerBanStore`**；登录成功后 `onAccountAuthed` 会解除风险 IP 的强制观战（`IPG:563-571`）。即"新 UUID 进服（成为未登录游客，可能被强制观战）→ `/login` 已有账号 → 被封禁的账号也能登录并恢复游玩"。**该链路由代码静态推导，未在日志中验证被实际利用（未确认）。**
3. **VPN/换网/移动数据切换**：风险按 IP 字符串，换出口即换键。
4. **有第二个账号**：风险 IP 只限制未登录与新注册，任何已有账号均可登录（设计如此，`IPG:557-561`）。
5. **Steam/非 IPv4 地址**：`module.kts:46-49` 对 `steam:*` 连接改写 UUID 来源；`IPG:82` 把 `steam:*` 判为本地 → 整个 IP 风控对其失效。当前服务器是否真有 Steam 连接**未确认**，但代码路径存在。

### Q4 🟠 阈值设计被重连路径旁路

- 设计意图（文档 `docs/account-system.md:166`、`docs/scripts-maintenance.md:3250`）：单次投票踢出不立刻影响同 IP 游客，累计 2 次才标记。
- 实测：窗口内 9 次踢出全部 `1/2`，阈值 0 次生效；而 5 个被踢 IP 通过"被封账号重连"路径被立即标记。10-04 23:28 案例中投票踢出后 5 秒即触发标记。
- 结论：实际触发结构是"**封禁（含 60 分钟投票封禁）→ 重连即标**"，阈值主要约束"不回来的人"，对"会回来的捣乱者"基本无效。

### Q5 🟠 与同 IP 多账号清理/其它观战来源的关系

- `forceObAutoCleaner.kts` 的同 IP 清理（`77-114, 133-173, 195-228`）：
  - 仅在线人数 ≥ `playerThreshold`（默认 14）时运行；
  - 只处理**已登录**玩家，按 IP 分组、保留等级最高/admin 的一个账号，其余踢出；默认保护 3++/4（`25-26, 90-93, 111`）；
  - 与 `IPG` **不共享数据**：`IPG` 的"允许同 IP 多账号"是硬编码策略（`IPG:675`）；清理逻辑不读风险 IP，清理踢出也不走 `ban()`，因此**不会**给 `IPG` 增加踢出计数或触发风险标记（`forceObAutoCleaner.kts:158-163` 直接 `player.kick`）。
- 结论：**技术上不打架**（无重复处罚、无数据污染），但存在两个策略相反的系统并存，容易让玩家/管理困惑。
- 真正的交互问题：`IPG` 强制的风险游客是**未登录**玩家，而 `forceObAutoCleaner` 的两个清理候选都只收已登录玩家（`:69`、`:82`），因此**风险游客不会被高人数清理释放**；`/ipguard release` 在风险仍生效时又拒绝释放（`IPG:728-735`）。结果：一个被连坐的游客可能在整个风险期（最长"最后一次重连+24h"）内持续占用观战位，只能自行退出或登录。
- 另一层：`securityGuard` 是**独立**的第二套 IP 风控（`security.ipBan.*` 键、临时 IP 封禁、连接/聊天/菜单限速，`securityGuard.kts:84-116,344-414,633-753,1021-1053`），与 `account.ipRisk` 互不读写；`securityGuard.kts:210-246` 只是读取账号风险用作观战来源诊断。两套系统同时存在意味着"IP 被封"和"IP 风险"是两件事，管理入口也不同（`/security` vs `/ipguard`），**没有冲突但有认知成本**。

### Q6 🟠 小号广播：误报公开化 + 隐私暴露 + 刷屏

- 量级：17 个自然日 293 条全服广播（日均 17、峰值 46/日、近 3 天 7~11/日）。
- 误报机制：只凭"24h 内同 IP 换身份"就公开断言"可能为小号"，公共出口（NAT/网吧/宿舍/家庭共享 WiFi）会大量误报；同一对身份还能反复播 11+11 次。
- 隐私：广播包含上一身份的**玩家名 + 完整游戏 UUID（24 字符 base64）+ 短 ID**（`IPG:288-295`），并把"两人同 IP"这一信息全服公开；对共享网络用户尤其不利。
- 与现有文档预期（"60 秒内不会重复广播，避免重连重复刷屏"，`docs/scripts-maintenance.md:3248`）存在明显差距。

### Q7 🟠 持久化 fail-open 与非原子写

- 见 §4.3：索引是快速否定判据（`IPG:379`），"记录存在但索引缺失"会静默放行；`markRiskIp`/`clearRiskIp` 的两次写库非原子（`IPG:472-474`、`550-551`），进程在两次写之间退出会造成不一致。
- 索引整体是"单个 setting 的多行字符串"，每次标记/解除/status 都整体读改写；单点损坏会一次性影响全部风险 IP 的判定。

### Q8 🟠 数据最小化/保留期缺失

- `account.ipLast.<ip>` 永久保留 IP→(账号主体 ID、游戏 UUID、玩家名、时间)，无过期无清理；`ipRisk`/`ipKick` 解除后留下 NULL 行。
- 风险原因字符串直接保存禁封/踢出理由（可能包含对其他玩家的指控、辱骂原文，如日志中的"乱特么抢别人核心"）。
- 这些数据都在 H2 明文库；`/ipguard check` 还会向 4 级/admin 显示旧版"IP→QQ 账号"绑定（`IPG:688,698`）。
- 隐私合规上没有外发：`ip2region` 查询是本地 xdb（仅启动时可能从配置 URL 下载数据库，`ipRegion.kts:59-81`），风险判定不向第三方发 IP。

### Q9 🟡 性能：总体开销小，但存在"游戏线程读库"的尾部风险

- 每次入服（含已登录玩家）：`PlayerJoin` → 延迟 3s → IO 线程执行 `loadLastIdentity`（1 次 `getSetting` 读）+ `saveLastIdentity`（1 次写）（`IPG:319-356`）→ 每个不同 IP 每次入服 1 读 1 写。
- 风险检查在游戏线程：`AssignTeamEvent`/`OnChat`/`PlayerJoin` 里的 `riskRecord` 在索引命中时会读库（首次读后进 `riskCacheByIp` 缓存），`markRiskIp` 在游戏线程做多次事务（单 IP 记录 + 索引读改写 + 遍历在线玩家）。
- 日志中窗口内有 1 条 `[数据库] 慢事务: getSetting cost=448ms thread=HeadlessApplication`（`D:\临时文件-mdtlog\error\script-load-restart-2026-10-07_14-09-19.log:807`，2026-10-07 16:26:28）。`getSetting` 被大量功能共用，**无法归因到 ipguard（未确认）**，但说明游戏线程上确实存在百毫秒级 DB 读的尾部风险；`IPG` 的 `riskRecord` 正是这类调用之一。无 `ipguard` 专属异常，总体开销可接受。
- `/ipguard check`/`status` 为管理员低频命令，会做多次同步事务（`IPG:686-707, 446-461`），可接受。

### Q10 🟡 可观测性不足

- 只有 4 类 logger：标记（475）、踢出计次（525）、拒绝注册（581）、身份切换（297/350）。缺少：风险解除、过期释放、强制观战/禁言实际发生数、`/ipguard` 管理操作审计、同一 IP 被重复标记次数/来源身份。
- 结果：本次审计能统计"标记了多少次"，但**无法回答"实际限制了多少人/多少注册被拒"**；管理员事后也难区分"风险IP限制"与"安全风控/今日游客观战"造成的观战（`docs/security-guard.md:88` 已提示需要多命令联合排查）。
- 标记日志不含操作者/触发身份（`operatorUid` 只进库、不进日志，`IPG:470-475`），只能靠 reason 文本推断。

### Q11 🟡 文案与配置脱节、代码细节不一致

- 玩家提示与拒绝注册文案硬编码"近24小时内"（`IPG:414, 577`），但实际时长由 `riskIpDurationMillis` 控制；改配置后文案会撒谎。
- `IPG` 的 `playerIp` 缺 `?: player.ip()` 回退（`IPG:402`），与同类脚本不一致；`con` 为空时按 `unknown` 放行（fail-open）。
- `status` 文案硬编码"单IP多账号: 允许"（`IPG:675`），若未来策略变化会误导管理。
- `activeRiskIps` 仅在 `guardEnabled=true` 时回写剔除过期索引（`IPG:459`），关闭期间过期项会留在索引里（无害但让 `status` 数字依赖后续访问）。
- 存在无调用方的代码：导出的 `isRiskIp`（`IPG:400`）全库无引用；同步版 `rememberIpIdentity`（`IPG:274-302`）已被异步版替代（实际调用链只走 `rememberIpIdentityAsync`/`scheduleRememberIpIdentity`，`IPG:319-373`），属维护噪音。

### Q12 🟡 旧版 IP 绑定表的兼容噪音

- `MdtIpAccountBindings` 已无写入方，但 `/ipguard check` 仍显示"旧IP绑定记录"、`/ipguard unbind` 仍作为管理功能存在（`IPG:688, 698, 737-744`），容易让管理误以为系统仍按"1IP=1账号"运行（实际策略相反）。

## 8. 建议（仅建议，未改任何代码）

> **决策状态（2026-10-17）**：本报告 §8 其余建议默认"**只留报告、不改代码**"（方案 C）；"风控补行为规则"类建议已被用户明确否决。详见 §11「用户决策记录」。

按"先降误伤、再补绕过、最后补观测"排序：

### 8.1 降低误伤 / 控制连坐面

1. **共享出口识别**：统计同一 IP 在 24h 内出现的不同主体数（`recentByIp` 已有素材），超过阈值（如 ≥5 个独立主体/USID）时把该 IP 标记为"共享出口"：可用"仅限制注册 + 不强制观战"或"只做提示"的降级策略，而不是全量连坐。
2. **配置化白名单/豁免**：为校园网、宿舍、网吧、已知家庭多设备出口提供 `exemptIps`/`exemptCidrs` 配置（不必改代码逻辑，`shouldIgnoreIp` 已有统一入口可扩展）。
3. **限缩"未登录强制观战"**：对风险 IP 的新游客可只限制"注册 + 聊天投票"，保留观战外的正常游玩，降低"新玩家完全无法体验"的伤害；或在提示里提供明确申诉渠道（加 QQ 群/wiki 链接）。
4. **续期上限**：风险到期时间改为 `min(首次标记 + 上限, 最近一次触发 + 24h)`，或仅在"新的不同封禁主体"触发时续期；纯重连尝试只踢出、不续期。这样单 IP 不会因为一个脚本化重连器被无限锁死。
5. **离线标记更保守**：离线封禁回退 `last_ip` 时，日志/管理面板标注"来自历史 last_ip，可能过期"，或改为只标记在线封禁的当前 IP。

### 8.2 补绕过面

6. **登录时校验封禁**：在 `finishLogin`（`accountAuth.kts:399-456`）补一次 `PlayerBanStore` 查询（当前只在连接阶段查），可同时堵住"新 UUID + /login 被封账号"链。
7. **风险判定覆盖新身份**：被封账号重连时，除当前 IP 外，把"该身份最近一次登录 IP"也纳入判断（`last_ip` 已有）；对新 UUID/新 USID 的游客记录"高风险来源 IP"供人工排查。
8. **Steam/未知地址策略显式化**：明确"Steam 连接地址不参与 IP 风控"是接受的风险，还是需要记录 `steam:*` 作为独立风控维度；当前"当成内网静默忽略"缺少说明。
9. **VPN 之外的兜底**：把风险 IP 与"封禁账号最近登录 IP 段"（/24）结合做辅助信号（仅提示，不做自动处罚，避免扩大误伤）。

### 8.3 广播/隐私治理

10. **广播降级**：默认改为仅管理员可见（`notifyAdmins`）或玩家信息面板展示，把"可能为小号"从全服广播降为管理线索；若必须保留全服广播，缩短文案、隐藏完整 UUID（只留短 ID）。
11. **去重窗口加长/按身份对冷却**：把 60s 去重扩展为"同一 IP 的同一身份对 10 分钟冷却"，并对"共享出口"抑制广播，可显著减少刷屏与误报。
12. **数据保留策略**：为 `account.ipLast.*`/`account.ipKick.*`/`account.ipRisk.*` 增加保留期清理任务（如 ipLast 90 天、ipKick 随过期删除行而非置 NULL），并在文档中声明 IP/身份数据的用途与保留期；`/ipguard check` 的旧 QQ 绑定展示建议移除或加审计日志。

### 8.4 持久化健壮性

13. **索引与记录一致性**：把索引从"强制否定判据"降级为缓存（索引未命中时回查单 IP 记录），或提供 `/ipguard reindex` 从单 IP 记录重建索引；`markRiskIp` 改为单事务写两条键（Exposed 事务内顺序写）或先写记录后写索引并容忍索引短暂滞后。
14. **物理删除过期行**：解除/过期时 `DELETE` 对应 setting 行（`MdtStorage` 目前 `setSetting(null)` 会保留 NULL 行），避免长期膨胀。

### 8.5 可观测性

15. **补日志**：风险标记日志带上"触发身份/触发场景（重连 or 管理封禁 or 阈值）"；增加解除/释放/强制观战/禁言/拒绝注册的次数日志；`/ipguard risk|unrisk|release` 记录操作管理员（可与 `/security` 的审计口径统一）。
16. **状态面板**：`/ipguard status` 增加"今日标记数 / 今日注册拒绝数 / 当前风险游客数 / 共享出口疑似 IP 数"；`/security status` 里区分显示"账号风险IP / 安全风控IP封禁"两类。
17. **性能观测**：把 `riskRecord` 的读库路径加轻量耗时日志（或统一走内存缓存 + 异步刷新），便于确认 448ms 慢事务是否来自风控链路。

### 8.6 与相邻系统的一致性

18. 在 `docs/account-system.md`/`docs/security-guard.md` 中把"账号风险 IP（限制未登录+注册，允许同 IP 多账号）"与"高人数同 IP 多账号清理（限已登录、保护 3++/4）"、"安全风控 IP 封禁（拒绝连接）"三者的适用条件并列说明；避免管理误用。
19. 评估"风险游客占位"：当在线人数接近上限时，是否需要把风险游客纳入观战清理候选（需人工确认策略，不建议直接改）。
